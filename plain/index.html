AI & agents · Case study

LawStack aiops

An operator console that takes Jira tickets to pull requests, one AI agent per lane.

  • 100+tickets taken to a pull request
  • < 1 hrtypical ticket to PR, down from hours
  • Dailystill the way we work
Problem
Every ticket went the same way: read it, branch, think it through, plan, review, build, test, open the pull request, update Jira. Most of those hours went on the same steps again, not on the hard part.
My role
I designed and built it alone, 128 commits in its first three weeks from April 2026. A small team of us still takes our tickets through it.
How it works
Each Jira ticket moves across a board of lanes: brainstorm, plan, review, pull request, implement, test. Every lane is a Claude Code agent with its own prompt and model, working in the ticket's own git worktree; its output streams live and is kept as a record. The thinking lanes run on Sonnet. Implementation runs on Opus, because that is where a weaker model thrashes.
Decisions
  1. No code before a person says yes. An agent writes code only after someone approves its brainstorm and plan. Approving commits both to the branch, opens a draft pull request and comments on the Jira ticket.
  2. One ticket, one worktree. Each ticket gets its own branch and working copy, so several can be in flight without stepping on each other.
  3. Agents check agents. Review and security agents go over the work, then the CI review verdict is read back from the pull request: a pass moves the ticket to done, a blocker sends it back to implement. This catches most mistakes before a person sees the pull request.
  4. A budget on every run. Each agent run has a cost warning and a hard stop (US$10 and US$30 for implementation), and the dashboard shows spend and throughput.
  5. Steps that resume. Approval is a chain of recorded steps (commit, push, open the pull request, notify Jira), so a failure picks up where it stopped instead of starting again.
Stack
Next.js 15, TypeScript, SQLite with Drizzle, Auth.js with Google sign-in, the Claude Code CLI, server-sent events, systemd and Caddy, and a one-command installer.

AI & agents · Case study

VIPTutors AI Suite

AI learning apps for speech practice, interview prep and writing, with payments and live tutoring.

  • 3AI learning apps
  • < 6 mobuilt end to end
  • 1platform for accounts, payments and tutoring
Problem
Students only got feedback in their paid lessons. Between lessons they practised alone, with no one to tell them what to fix.
My role
I built it end to end, mostly on my own, in under six months in 2023: the AI apps and the platform around them.
How it works
Three apps on one platform: speech practice, interview prep and writing. A specialist service, SpeechSuper, scores the speech; OpenAI then turns the scores and the transcript into feedback a learner can act on, and the next thing to practise.
Decisions
  1. One shared platform. Every app shares one set of accounts, Stripe payments and Zoom tutoring, so a new app meant building only the learning part.
  2. Score first, then explain. Scoring is left to a service built for it, and the language model only explains the result, so the feedback rests on a measurement rather than a guess.
  3. Practice that leads to a tutor. The AI covers the days between lessons and points to a live Zoom tutor for what it cannot fix.
Stack
Laravel, OpenAI, SpeechSuper, Stripe and Zoom.

MultiPortal

A multi-tenant cloud platform where service providers run servers, networks and backups for their customers.

The case study: one UI standard for the whole product, written for people and coding agents alike.

  • Onestandard across the product
  • Anytheme, light or dark
  • Everychange checked automatically
Problem
The product grew screen by screen over years, and it showed: pages looked and behaved differently, custom brand colours could make text hard to read, and dark mode and translations were uneven. Coding agents copied whichever old page was nearest, spreading the inconsistency.
My role
I led it end to end: wrote the standard, built the kit and its checks, and moved the app onto it.
How it works
The standard lives in its own versioned kit: components, page templates and documentation with a live preview of each. Every guideline says what to build and which template to start from, and automated checks flag anything that breaks the rules.
Decisions
  1. Written for agents too. Most UI code is now written with coding agents, so the guidelines are built for them as well: an index of the rules most often broken, and a step that loads the right page before any UI is written. The agent reads the rule instead of copying an old page.
  2. Checks that block. Automated checks run on every change, so drift is caught in review rather than by users.
  3. Colour never carries meaning. Brand colours are for the brand only. Status and warnings use fixed colours, so any theme, light or dark, stays readable.
  4. Its own package. Components, templates and guidelines ship as a versioned kit, instead of copies living inside the app.
Stack
PHP and Bootstrap, with automated checks in CI.

  • Usage meteringMeasures what every customer uses, so usage turns straight into a bill.
  • Alert integrationsSends alerts to the chat and on-call apps a team already uses.
